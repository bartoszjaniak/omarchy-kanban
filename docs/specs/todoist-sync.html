Synchronizacja tablicy z Todoist

Tablica TODO / In Progress / DONE jako jedyne źródło prawdy oraz dwukierunkowa synchronizacja statusów z Todoist: import przez AI, idempotentny sync w tle, konflikt rozstrzygany na korzyść ręcznej zmiany, token wyłącznie ze zmiennej środowiskowej.

1. Cel i uzasadnienie

Tablica TODO / In Progress / DONE jest jedynym źródłem prawdy o tym, co robimy — ale część zadań użytkownika żyje w Todoist (telefon, współdzielone projekty, zadania cykliczne). Ręczne przepisywanie ich na tablicę to praca, której nikt nie wykonuje regularnie. Efekt: tablica kłamie, a Todoist rośnie w zaległościach.

Cel: jedno miejsce decyzyjne (tablica) i automatyczne odzwierciedlenie statusów w obie strony. Import nowych zadań pozostaje decyzją AI — tylko ona potrafi ocenić, czy zadanie „kup mleko” da się zrobić na komputerze.

2. Opis problemu

  • Zadania z Todoist na dziś i zaległe nie trafiają na tablicę; użytkownik nie wie, co realnie może zrobić przy komputerze.
  • Ukończenie zadania w jednym systemie nie jest widoczne w drugim.
  • Cofnięcie karty z DONE („jednak tego nie zrobiłem”) nie przywraca zadania w Todoist.
  • Ręczne kopiowanie tytułów, terminów i statusów jest kosztowne i nieaktualne w ciągu godziny.

3. Przyjęte rozwiązania

  1. Import przez AI. Core udostępnia listę kandydatów (zadania Todoist na dziś i zaległe, jeszcze niezlankowane). AI (sesja OpenCode, skill kanban-triage) ocenia, które da się wykonać na komputerze, i importuje je przez CLI. Core nie importuje nic automatycznie.
  2. Link 1:1 karta ↔ zadanie Todoist przez kolumnę tasks.todoist_id (unikalny indeks częściowy). Bez osobnej tabeli mapowań.
  3. Stan zdalny i znacznik zdarzeń na karcie:
    • tasks.todoist_state (open / closed, NULL = brak linku) — ostatni znany stan zadania w Todoist, daje idempotencję close/reopen;
    • tasks.todoist_seen_at (epoch, 0 = brak) — znacznik ostatniego rozliczonego ukończenia w Todoist (completed_at), żeby nakładające się okna zapytań nie stosowały tego samego zdarzenia dwa razy.
  4. Sync w tle w Core (pętla co 60 s, obok istniejącej pętli archiwizacji). Push przed pullem; sieć nigdy pod lockiem bazy; jeden cykl naraz (single-flight).
  5. Konflikt: wygrywa ręczna zmiana. Jeżeli karta była modyfikowana po ostatniej udanej synchronizacji, Todoist nie nadpisuje jej statusu — zamiast tego stan lokalny jest wypychany (reopen), a zdarzenie ukończenia jest oznaczane jako rozliczone.
  6. Archiwum: karty archived są tylko pushowane (close zaległego zamknięcia), nigdy pullowane — archiwum nie wskrzeszamy.
  7. Usuwanie tylko lokalne. task rm linkowanej karty usuwa ją z tablicy i nie dotyka Todoist (brak mechanizmu usuwania w widgecie, więc to ścieżka CLI).
  8. Token wyłącznie ze zmiennej środowiskowej TODOIST_API_TOKEN. Brak tokenu = integracja wyłączona, Core działa bez zmian.
  9. Bez nowych zależności. Czas w epoch sekundach + własny formatter ISO 8601 UTC (~20 linii).
  10. Bez zmian w widgecie. Link do Todoist nie ma reprezentacji wizualnej; stan integracji widać przez omarchy-kanban todoist status.

5. Wzorce architektoniczne

  • Snapshot → sieć → zapis. Jedno krótkie zajęcie Mutex<Store> na odczyt, żądania HTTP bez locka, jedno krótkie zajęcie na zapis. std::sync::Mutex i rusqlite są synchroniczne; guard nie może przeżyć .await.
  • Maszyna stanów per karta zamiast porównywania zegarów: (status lokalny, todoist_state) → akcja; todoist_seen_at → czy zdarzenie zdalne już rozliczone.
  • Idempotentne przejścia. Powtórzony cykl nie wysyła drugi raz tego samego close/reopen; powtórzone okno zapytania nie stosuje drugi raz ukończenia.
  • Compare-and-set na statusie. Pull zapisuje status tylko wtedy, gdy karta nie zmieniła się od snapshotu (WHERE updated_at = <snapshot>). Zapis stanu zdalnego (todoist_state) nie jest CAS-owany — to metadana o Todoist, nie decyzja użytkownika.
  • Single-flight. Pętla i endpoint POST /api/todoist/sync współdzielą tokio::sync::Mutex; drugi wywołujący dostaje busy zamiast drugiego cyklu.
  • Częściowy unikalny indeks tasks(todoist_id) WHERE todoist_id IS NOT NULL blokuje podwójny import tego samego zadania.
  • Miękka degradacja. Brak tokenu, brak sieci, 401, 429, 5xx: integracja milczy, Core i tablica działają dalej; błąd widoczny w todoist status i logu.

7.2 API Todoist (v1, TODOIST_API_URL nadpisywalny dla testów)

Paginacja kursorowa: limit=200, dopóki next_cursor != null. Limit dostawcy: 1000 żądań / 15 min — nasz cykl to 1–3 żądania.

Kontrakt odpowiedzi: close/reopen mogą zwrócić 200 lub 204 bez ciała — sukces czytamy ze statusu HTTP, ciało parsujemy tylko przy błędzie. close już zamkniętego zadania (400) traktujemy jak sukces (state='closed'); reopen nieaktywnego/cyklicznego (400) jak sukces (state='open'); 404 = zadanie zniknęło → odlinkowanie. 401/429/5xx/timeout = błąd cyklu.

8. Przepływy danych

8.1 Import (AI)

  1. AI: omarchy-kanban todoist candidates --json.
  2. Core: GET /tasks/filter?query=today | overdue, wszystkie strony; odrzuca id już zlinkowane; zwraca listę.
  3. AI ocenia każde zadanie: „da się zrobić przy komputerze?” (tak → import; nie → pomija i mówi użytkownikowi dlaczego).
  4. AI: omarchy-kanban todoist import <id>….
  5. Core: dla każdego id GET /tasks/{id} (404 → skipped), tworzy kartę status=todo (lub wskazany), notes = opis + Termin: … gdy jest, todoist_id, todoist_state='open', todoist_seen_at=now. Duplikat → skipped: already_linked.

8.2 Cykl synchronizacji (sync_once(at))

Wejście: at (epoch), klient, snapshot linków (id, todoist_id, status, updated_at, todoist_state, todoist_seen_at) oraz last_sync z meta.

  1. Push (karty todo|doing|done, oraz archived — tylko w tę stronę):
    • status ∈ {done, archived} + state != closed → POST close → state='closed'
    • status ∈ {todo, doing} + state == closed → POST reopen → state='open'
    • 404 → odlinkuj (karta zostaje), errors += wpis
    • 400 → odpowiednio closed/open (już w tym stanie), bez błędu
    • błąd jednej karty nie przerywa cyklu; reszta kart leci dalej
  2. Pull, tylko jeśli istnieje choć jedna karta status != done|archived z todoist_id (nie ma czego pullować → zero żądań): GET /tasks/completed/by_completion_date?since=<last_sync - 300 s>&until=<at>, since = at - 7 dni gdy brak last_sync. Okno jest przycinane: nie starsze niż 89 dni (since >= at - 89 dni) i zawsze since < until (odporność na cofnięty zegar; inaczej każde żądanie kończyłoby się 400). Dla każdego ukończenia (todoist_id, completed_at):
    • completed_at <= todoist_seen_at → już rozliczone, pomiń;
    • karta nietknięta (updated_at < last_sync, a przy braku last_sync — zawsze „nietknięta”) → status='done', done_at=at, state='closed', todoist_seen_at=completed_at;
    • karta ruszona ręcznie po last_sync → wygrywa tablica: POST reopen, state='open', todoist_seen_at=completed_at (zdarzenie rozliczone, nie wróci).
  3. Zapis (jedna transakcja): statusy i done_at przez compare-and-set (WHERE id=? AND updated_at=<snapshot updated_at>); todoist_state i todoist_seen_at bezwarunkowo; unlink; meta.todoist_sync_at = at tylko gdy cykl nie zwrócił błędów; meta.todoist_last_error ustawiany/wyczyszczony.
  4. Log tylko przy zmianach lub błędach (bez tokenu).

9. Wymagania niefunkcjonalne

  • Bezpieczeństwo: token tylko w env usługi (drop-in + EnvironmentFile 0600); brak tokenu w argv, URL, logach i odpowiedziach HTTP; nowe endpointy rejestrowane przed .layer(guard), więc podlegają Bearer + loopback Host.
  • Odporność: żaden błąd sieci nie może zatrzymać Core ani pętli; timeout żądania 10 s, połączenie 5 s; MissedTickBehavior::Skip.
  • Locki: brak await pod MutexGuard; jedno zajęcie locka na odczyt, jedno na zapis.
  • Współbieżność: jeden cykl naraz (tokio::sync::Mutex + try_lock).
  • Wydajność: jeden cykl = 1–3 żądania HTTP poza push/pull; bez N+1.
  • Zależności: zero nowych w Cargo.toml (Cargo.lock bez zmian).
  • Zgodność wstecz: tasks dostaje kolumny przez ALTER TABLE przy Store::open; stare karty nietknięte, todoist_* NULL/0; add() przechodzi na jawną listę kolumn; row()/SELECT obejmują nowe pola; widget bez zmian (nieznane pola ignoruje).
  • Język: komunikaty CLI po polsku, kod i testy po angielsku (jak reszta repo).
  • Formatowanie: cargo fmt --check oraz cargo clippy -D warnings czyste.

11. Decyzje użytkownika

  1. Import tylko przez AI/CLI — Core nie importuje automatycznie; AI decyduje, które zadania „da się zrobić na komputerze”.
  2. Konflikt: wygrywa ręczna zmiana — karta ruszona po ostatniej synchronizacji nie jest nadpisywana przez Todoist.
  3. Usuwanie: brak mechanizmu usuwania w widgecie; task rm linkowanej karty usuwa ją tylko lokalnie, bez DELETE w Todoist.
  4. Repozytorium: projekt nie był w gicie; założone repo, stan wyjściowy w commicie bazowym, praca na feature/todoist-sync.
  5. Klucz API: przez zmienną środowiskową, ustawianą przygotowanym skryptem (todoist-token.py), bez wpisywania sekretu do repozytorium.

12. Otwarte pytania i decyzje

  • Zadania cykliczne: po close Todoist przesuwa termin wystąpienia. Karta zostaje DONE, więc kolejne wystąpienie nie trafi na tablicę automatycznie. Świadome ograniczenie (test #11 pilnuje braku błędu i pętli).
  • Edycja tytułu/notatek nie jest synchronizowana w żadną stronę — tylko statusy (test #18).
  • Reopen wykonany w Todoist nie wskrzesza karty DONE — tablica jest autorytatywna dla stanu ukończenia (test #19).
  • Składnia filtra today | overdue jest zewnętrznym kontraktem dostawcy; 400 z API trafi do todoist status, kandydaci będą puste. Nie testujemy.
