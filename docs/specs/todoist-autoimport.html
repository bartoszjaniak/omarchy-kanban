Auto-import z Todoist (timer + AI)

Automatyczna decyzja o imporcie zadań z Todoist na tablicę: timer systemd użytkownika budzi skrypt orkiestrujący, który przez opencode run pyta model o ocenę kandydatów i importuje wykonalne. Osobny składnik poza Core, zero nowych zależności, brak powiadomień — tylko journald.

Cel i uzasadnienie

Dziś import z Todoist wymaga człowieka: AI w sesji woła omarchy-kanban todoist candidates, ocenia zadania i importuje wykonalne. Użytkownik chce, żeby działo się to samo, co 2 godziny, bez udziału człowieka — karty z zadaniami „do zrobienia przy komputerze" mają czekać na tablicy.

Push/pull statusów (Core, pętla 60 s) działa już bez zmian. Ten dokument dodaje wyłącznie automatyczną decyzję o imporcie.

Opis problemu

  • Decyzja „czy zadanie da się zrobić przy komputerze" wymaga osądu — nie da się jej zapisać regułą po etykiecie czy projekcie.
  • Core nie może wołać modelu: sekrety, koszt, opóźnienia i awarie modelu nie mogą dotykać pętli synchronizacji (decyzja z docs/specs/todoist-sync.md §4).
  • Ręczne uruchamianie AI działa, ale wymaga obecności użytkownika.
  • Awaria musi być widoczna: „brak kandydatów" (normalny stan) i „integracja wyłączona / token nieważny / model padł" (błąd) nie mogą wyglądać tak samo.

Przyjęte rozwiązanie

Osobny składnik poza Core: timer systemd użytkownika → skrypt orkiestrujący → model przez opencode run → CLI omarchy-kanban todoist import.

  1. Timer agent-kanban-todoist-import.timer budzi usługę co 2 godziny.
  2. Usługa agent-kanban-todoist-import.service (Type=oneshot) uruchamia ~/.local/bin/omarchy-kanban-todoist-import.
  3. Skrypt sprawdza omarchy-kanban todoist status --json: enabled=false → wyjście 0 (integracja wyłączona), last_error → ostrzeżenie w logu (synchronizacja zgłasza problem, import i tak próbuje).
  4. Skrypt pobiera omarchy-kanban todoist candidates --json (CLI → HTTP Core; token Todoist zostaje w usłudze Core, skrypt go nie widzi).
  5. Skrypt buduje prompt z listą kandydatów (maks. 100, w kolejności z API) i woła opencode run --standalone --model <model> "<prompt>", żądając wyłącznie JSON-a: {"import":[{"id":"…","reason":"…"}]}.
  6. Skrypt waliduje odpowiedź i woła omarchy-kanban todoist import <id>… dla poprawnych pozycji.
  7. Błędy: jedna linia w journald, kod wyjścia ≠ 0. Bez powiadomień.

Wzorce architektoniczne

  • Sidecar / orkiestrator poza domeną — Core pozostaje jedynym właścicielem danych; skrypt używa wyłącznie publicznego CLI.
  • Niezaufane źródło — model nie ma żadnych uprawnień; jego odpowiedź jest walidowana (id ∈ kandydaci, limity), a decyzje wykonuje skrypt.
  • Idempotencja przez domenę — powtórzony import kończy się already_linked w add_linked; skrypt nie utrzymuje własnego stanu.

Interfejs

7.1 CLI

Nowa flaga istniejącej komendy:

omarchy-kanban todoist status --json   # {"enabled":bool,"last_sync":int|null,"last_error":str|null,"linked":int}

Skrypt:

omarchy-kanban-todoist-import            # pelny cykl (timer)
omarchy-kanban-todoist-import --dry-run  # pokaz decyzje modelu, nic nie importuj

Zmienne środowiskowe (domyślne w skrypcie, nadpisywane w unicie/drop-inie):

ZmiennaDomyślnieZnaczenie
KANBAN_IMPORT_MODELopencode/glm-5.3-flash-freemodel dla opencode run
KANBAN_IMPORT_LIMIT10maks. liczba importów w jednym cyklu
KANBAN_IMPORT_MAX_CANDIDATES100ile kandydatów trafia do promptu
KANBAN_BIN / OPENCODE_BINomarchy-kanban / opencodenadpisania ścieżek (testy, nietypowa instalacja)

7.2 Prompt (stały tekst w skrypcie)

Tekst jest częścią kontraktu: zmiana treści = zmiana zachowania. Zmienne wstawiane są tylko w miejscu <<<ZADANIA>>>.

Jestes filtrem zadan. Otrzymasz liste zadan z Todoist (JSON).
Zdecyduj, ktore z nich da sie wykonac przy komputerze, siedzac przed nim.

Komputerowo wykonalne: pisanie, kodowanie, wysylanie maili i ofert, zamawianie
rzeczy online, wypelnianie formularzy, research, rozmowy, platnosci, rezerwacje.
Niewykonalne: prace fizyczne w domu i warsztacie (sprzatanie, mycie, malowanie,
odkamienianie, naprawy, montaz), wizyty, zakupy w sklepie stacjonarnym.
Brak opisu nie jest bledem - oceń po tresci zadania.

Zasady odpowiedzi:
- Zwroc WYLACZNIE obiekt JSON, bez prozy, komentarzy i blokow markdown.
- Format: {"import":[{"id":"<id>","reason":"<jedno zdanie, max 120 znakow>"}]}
- "id" kopiuj doslownie z listy; nigdy nie wymyslaj ani nie modyfikuj id.
- Zadanie niewykonalne po prostu pomiń (nie wypisuj go).
- Gdy nic nie jest wykonalne: {"import":[]}

Zadania:
<<<ZADANIA>>>

Zadania wstawiane jako JSON, każde z polami: id, content, description (przycięte do 300 znaków), due. Bez etykiet, priorytetu i projektu — nie wpływają na decyzję, a zwiększają wariancję.

7.3 Kontrakt odpowiedzi modelu

Zasady parsowania i walidacji:

  1. Znajdź pierwszy { w odpowiedzi i parsuj od niego json.JSONDecoder().raw_decode (stdlib) — proza wokół i nawiasy w stringach nie psują parsowania.
  2. Brak JSON-a, brak klucza import, import nie jest listą, albo lista istnieje, lecz żaden element nie przeszedł walidacji → błąd cyklu: log + exit 1 (to awaria warstwy AI, nie „brak zadań"). Wyjątek: import: [] to poprawna odpowiedź „nic nie jest wykonalne" → exit 0.
  3. Element niebędący obiektem, id niebędący stringiem albo id spoza kandydatów z tego samego wywołania → element odrzucony, log z powodem (spoza_kandydatow, duplikat, zly_ksztalt).
  4. Duplikaty id → jedno wystąpienie (pierwsze).
  5. Kolejność zachowana jak w odpowiedzi modelu; po deduplikacji lista przycinana do KANBAN_IMPORT_LIMIT (nadmiar logowany jako ponad_limit).
  6. reason jest opcjonalne (brak = ""), przycinane do 120 znaków, trafia tylko do logu. Nie jest przekazywane do Core.
  7. Odrzucenie jest per element: poprawne id są importowane, reszta logowana. Gdy model zwrócił same niepoprawne elementy → brak wywołania import, exit 1 (§7.3 pkt 2). Pusta lista import: [] → exit 0.

7.4 Jednostki systemd

# agent-kanban-todoist-import.service
[Unit]
Description=Kanban: auto-import z Todoist (AI)
After=network.target
ConditionPathExists=%h/.local/bin/omarchy-kanban-todoist-import

[Service]
Type=oneshot
ExecStart=%h/.local/bin/omarchy-kanban-todoist-import
Environment="PATH=..."
Environment=OPENCODE_BIN=...
Environment=KANBAN_IMPORT_MODEL=opencode/glm-5.3-flash-free
StandardOutput=journal
StandardError=journal
SyslogIdentifier=kanban-todoist
RuntimeMaxSec=15min
UMask=0077

# agent-kanban-todoist-import.timer
[Unit]
Description=Kanban: auto-import z Todoist co 2 godziny

[Timer]
OnCalendar=*-*-* 00/2:05:00
Persistent=true
AccuracySec=1min
RandomizedDelaySec=5min
Unit=agent-kanban-todoist-import.service

[Install]
WantedBy=timers.target
  • PATH — ta sama wartość, którą install.py wpisuje do usługi Core.
  • OPENCODE_BIN — shutil.which("opencode") w chwili instalacji; gdy nie znaleziony, wpisujemy opencode i polegamy na PATH.
  • Service nie ma [Install] (aktywuje go timer); TimeoutStartSec zbędne przy RuntimeMaxSec.
  • Token Todoist nie trafia do tych jednostek.

7.5 Instalacja (install.py)

  1. private_write skryptu do ~/.local/bin/omarchy-kanban-todoist-import + chmod 0755.
  2. private_write obu jednostek do ~/.config/systemd/user/.
  3. systemctl --user daemon-reload.
  4. systemctl --user enable --now agent-kanban-todoist-import.timer.
  5. systemctl --user restart agent-kanban-todoist-import.timer (przeliczenie harmonogramu po zmianie OnCalendar).
  6. loginctl enable-linger "$USER" — bez tego timer staje po wylogowaniu. Nieudane wywołanie (brak loginctl, polkit) → ostrzeżenie, nie błąd instalacji.
  7. --no-timer: pomija kroki 2–6 i wykonuje systemctl --user disable --now agent-kanban-todoist-import.timer (jeśli timer istnieje), żeby wyłączony nie został aktywny z poprzedniej instalacji.

Drop-in 10-todoist.conf (token) jest osobnym plikiem i przeżywa reinstalację.

Przepływy danych

8.1 Cykl (co 2 h)

  1. flock -n na $XDG_RUNTIME_DIR/kanban-todoist-import.lock; gdy zmienna pusta — /run/user/<uid>, a gdy katalog niedostępny — katalog tymczasowy. Zajęty → log „poprzedni cykl trwa", exit 0.
  2. todoist status --json (timeout 30 s). enabled=false → log, exit 0. last_error → log ostrzeżenia, kontynuuj.
  3. candidates --json (timeout 30 s). Pusto → log, exit 0 bez wołania modelu.
  4. Prompt (maks. KANBAN_IMPORT_MAX_CANDIDATES zadań; nadmiar → log kandydaci=N do_promptu=M) → timeout 180 opencode run --standalone --model <model> <prompt>. Błąd/timeout → log, exit 1.
  5. Parsowanie i walidacja (§7.3). Zero poprawnych id → log, exit 0.
  6. --dry-run: wypisz decyzję, exit 0, bez importu.
  7. import <id>… (timeout 120 s, jedno wywołanie). Wynik CLI logowany.
  8. Podsumowanie w jednej linii: todoist-import: cykl kandydaci=N do_promptu=M import=K odrzucone=J.

Każda linia logu ma prefiks todoist-import: (journald dodaje jeszcze SyslogIdentifier=kanban-todoist).

Wymagania niefunkcjonalne

  • Zero nowych zależności — Python 3 stdlib; w Rust tylko flaga --json (bez nowych crate'ów).
  • Sekrety — skrypt nie czyta tokenu Todoist ani tokenu Core (CLI robi to sam); token nie trafia do argv, unitu ani logu. reason z modelu nie trafia do Core.
  • Izolacja — awaria skryptu nie dotyka agent-kanban.service.
  • Odporność — flock + RuntimeMaxSec + timeouty na każde wywołanie zewnętrzne; brak kumulacji po suspendzie (Persistent=true nadrabia jedno uruchomienie).
  • Koszt — 12 wywołań modelu dziennie, prompt ≤ 100 kandydatów × ~300 znaków.
  • Limity Todoist — kilka żądań na cykl, daleko od 1000/15 min.
  • Observability — jedna linia podsumowania na cykl; podgląd journalctl --user -u agent-kanban-todoist-import -n 50.

Decyzje użytkownika

  1. Auto-import ma działać co 2 godziny (nie raz dziennie).
  2. Przy błędzie bez powiadomień — tylko log w journald.
  3. Model konfigurowalny; domyślnie darmowy z opencode, bo typesafe/jev-router z OpenRouter nie ma aktywnych endpointów (sprawdzone: endpoints: [], ~typesafe/jev-latest nie istnieje w tej instalacji opencode).
  4. Decyzja o imporcie pozostaje poza Core (skrypt + timer), zgodnie z decyzją ze specyfikacji sync.

Otwarte pytania i decyzje

  • Niedeterminizm. opencode run nie udostępnia temperature/seed; stabilność decyzji zapewnia stały prompt (§7.2) i przypięty model, nie powtarzalność. Zmiana modelu = zmiana zachowania.
  • Zadania cykliczne. Kandydaci to today | overdue; zadanie cykliczne po zamknięciu wraca z nowym id i może wrócić na tablicę po imporcie. Świadome: karta w DONE nie jest duplikowana, ale ten sam tytuł może pojawić się drugi raz.
  • Odrzucone zadania wracają do promptu co 2 h — koszt tokenów, nie poprawność. Główna motywacja przyszłego stanu „seen/skipped" w meta.
  • Follow-up (świadomie poza zakresem): trwały stan odrzuconych, powiadomienia, fallback między modelami, filtry per projekt, is_recurring w kandydatach.
  • Model domyślny można zmienić jedną linią w unicie; nie blokuje wdrożenia.
